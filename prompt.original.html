One-shot prompt: browser-native 2-layer induction transformer visualizer

Build a complete, polished, interactive web app that runs a two-layer attention-only toy transformer entirely in the browser with WebGPU, while providing TransformerLens/CircuitViz-style interpretability visualizations for its induction circuit. Use WebAssembly as a transparent fallback. Do not require a backend, inference API, model hub, or transmission of user data anywhere.

Role and deliverable

Deliver a production-quality, self-contained web app that works by opening its entry HTML file directly in a browser.Assume the user is studying a compact induction circuit and wants short, exploratory feedback loops in the browser.

Prefer a small Vite + TypeScript project, but avoid heavy dependencies. If WebGPU compute is not available, the same model must run through the WebAssembly path with identical outputs (within normal floating-point tolerance) and the UI must explicitly show the active backend. The app must still be usable without any network connection after it is downloaded or checked out.

Exception to the no-backend rule: the initial build may download the TransformerLens weights once and convert them into a small, browser-local artifact. Once converted, the app itself must load only from local project files, IndexedDB, or localStorage; it must never transmit tokens, text, activations, weights, telemetry, or analytics.

Target model

Implement and visualize this exact TransformerLens configuration:

HookedTransformerConfig(
  d_model=768,
  d_head=64,
  n_heads=12,
  n_layers=2,
  n_ctx=2048,
  d_vocab=50278,
  attention_dir="causal",
  attn_only=True,
  seed=398,
  use_attn_result=True,
  normalization_type=None,
  positional_embedding_type="shortformer"
)

Model architecture, semantics, and naming should follow TransformerLens as closely as practical:

  • Embedding: learnable token embedding plus learnable shortformer position embedding.
  • Two causal, multi-head self-attention blocks with no MLPs or LayerNorm.
  • Preserve named intermediate hooks: embeddings, Q/K/V/Z, attention scores and patterns, head results, and per-head residual contributions.
  • Compute per-head output as z @ W_O, and make direct logit attribution straightforward.
  • Model identifiers to expose in UI and docs: TransformerLens-style configuration and callummcdougall/attn_only_2L_half.

Keep the operation graph synchronized with the WebGPU backend. Implement fallback logic in the shared numerical core so attention math, caching, and all analysis results remain available on the WebAssembly backend.

Model data and provenance

Use the pretrained weights from callummcdougall/attn_only_2L_half, file attn_only_2L_half.pth, reconstructed from TransformerLens 2.17.0-compatible state format. The app must show provenance, license status if determinable, parameter counts, and artifact checksum.

Choose one of these approaches and document the choice:

  • Preferred: check in or generate a compact FP16/NPY artifact that can be loaded synchronously as bytes in the browser.
  • Alternative: reconstruct from raw binary artifacts already present in the repository.
  • Development-only fallback: if real weights cannot be embedded in the final answer, create a deterministic synthetic model with the exact architecture and clearly label it as “synthetic — not pretrained”; do not misrepresent it as the pretrained model.

If a conversion utility is included, it may read the upstream checkpoint during development and write a local artifact. It must be optional and completely unnecessary after the browser app is built. Never dynamically fetch model data from Hugging Face, GitHub, or any other remote at runtime.

The production artifact should remain comfortably small enough for local iteration.

Runtime and privacy requirements

  • All model inference, activation caching, analysis, and visualization happen in the browser.
  • WebGPU is the primary backend. Detect missing hardware/API support and transparently fall back to WebAssembly.

Interactions and UI

Provide a clean, information-dense app shell and a responsive but research-oriented layout. Its workflow should feel like CircuitViz meets Transformer Explainer.

  • Prompt controls: editable token text, sequence length, random-token sequence generation, replay/step controls, sampling parameters if generation is included, and a run/cache button.
  • Token table: show token ID, source key, layer probabilities, and predicted token; highlight the repeated halves, BOS, first half, second half, and the induction target.
  • Discuss furtherActivation explorer: list the full activation cache in a searchable, sortable tree or table. Export selected tensors to JSON or CSV locally from a download button.
  • Top attention views: default to per-layer grids of head-by-dest/source attention heatmaps with tokens on both axes, perpetual causal masking for impossible positions, tooltips with exact values, color scale controls, and selectable layer/head cards.
  • Detail view: after selecting a head, show an enlarged attention heatmap with configurable destination/source bands, induction stripe overlays, and exact matrix values.
  • Circuit graph: render an interactive node-link diagram for tokens, heads, and the induction circuit. Node size/color can encode score or effect. Edge labels show paths and attention relations. Include static, deterministic layout for the canonical circuit diagram.
  • Timeline and run stats: total runtime, prefill/cache build time, sequence length, backend, model mode, and memory usage if available.

Interpretability analyses

  1. Attention head classifier: a configurable grid showing each layer/head with score labels, detector thresholds, and reasons for the current classification.
  2. Per-token loss and logits: show next-token loss and the layer-0/layer-1 direct logit attribution for each head, including a combined layer attribution chart. Explain the induction-period improvement in plain English.
  3. Ablation experiments: ability turn off a head for zero ablation and measure the effect on loss and attention scores.
  4. Circuit composition:
    • compute Q, K, and V composition scores between layer-0 and layer-1 heads,
    • define the score consistently as ||W_AB||_F / (||W_A||_F * ||W_B||_F),
    • support all pairs of layer-0 OV and layer-1 QK/OV circuits,
    • highlight layer-0 previous-token head → layer-1 induction-head K-composition.
  5. End-to-end induction narrative: show the canonical path: first-half token A → previous-token head at the first B → writes previous-token information into the residual/K-vector → second-half A queries through K-composition → attends to first B → OV circuit promotes the next token B. Link each narrative step to the exact tokens, attention cells, tensors, and weights involved.

Transformer Explainer-inspired presentation

Borrow the strongest UX ideas from the reference, but do not copy its design verbatim:

  • progressive disclosure: simple overview first, then expandable layer/head and tensor detail,
  • flow diagrams that let users inspect underlying computation step by step,
  • color-coded tensor shapes and readable descriptions for each operation,
  • hover and selection coordination between attention cells, token chips, graphs, and selected tensor rows,
  • realistic generated tokens and attention animation that aid intuition without obscuring exact values.

Data, state, and performance

  • Keep model parameters and inferred activations in typed arrays or GPU buffers.
  • Cache activation results in memory and, if necessary, IndexedDB for faster subsequent local runs.
  • Debounce interactive filters and redraw requests.
  • Provide efficient batched analysis; for example, repeated runs should not materialize the full 50278-vocabulary logits unless needed.
  • Keep sequences short by default and validate inputs before dispatching GPU work.
  • Stop computing as soon as a WebGPU device is lost or invalidated.

Quality and accessibility

  • compact and comfortable densities, and keyboard navigation.
  • Give every visualization an accessible table or text summary.
  • Use sufficient contrast and do not rely on color alone; show exact values or symbols in tooltips and accessible summaries.
  • Preserve zoom and pan for heatmaps and graphs while keeping controls keyboard reachable.
  • Handle failed runs with clear, actionable UI states.

Testing and verification

Provide a self-contained verification page or panel that proves numerical and privacy correctness:

  • Numerical parity: include fixture tensors and compare WebGPU and WebAssembly outputs at several sequence lengths.
  • Model parity: compare a sample forward pass and cached activations with expected values from TransformerLens if possible; otherwise include deterministic synthetic fixtures.
  • Analysis correctness: unit-test detector diagonals, induction scoring, direct logit attribution, ablation effects, and composition scores.
  • Interaction tests: verify backend switching, token selection, attention heatmap rendering, export, and failure/empty states.

Run the project’s build and test commands and report results. If WebGPU is unavailable in the build environment, tests must still cover the WebAssembly path and use automated stubs for the WebGPU API.

Documentation and structure

Document in README.md:

  • setup, build, development, and test commands;
  • WebGPU and WebAssembly browser support, with expected fallback behavior;
  • model provenance, artifact format, conversion instructions, and expected checksum;
  • interpretability methods, formulas, thresholds, and limitations;
  • the induction circuit narrative and the exercise identities that the app reproduces.

Organize source by domain — for example backend adapters, model implementation, analysis, visualization, UI state, tests, and documentation — and use small, focused modules rather than a monolithic file. Add concise inline comments only where formulas or numerical semantics are non-obvious.
