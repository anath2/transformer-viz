One-shot prompt: browser-native 2-layer induction transformer visualizer

Build a complete, polished, interactive static web app that runs a two-layer attention-only toy transformer entirely in the browser with WebGPU, with a WebAssembly fallback, and provides TransformerLens/CircuitsVis-style interpretability visualizations of its induction circuit, reproducing the analyses of ARENA chapter 1.2 (“Intro to Mech Interp”). There is no backend, no inference API, and no runtime model hub, and no user data is sent anywhere. The app is a teaching aid for students working through the ARENA material. It is deployed as a private static site on Cloudflare Pages and shared only with those students.

Resolved decisions

These choices are final. Do not revisit them; implement them.

HostingStatic Vite build served over HTTP(S): vite preview locally and Cloudflare Pages in production. Opening the build from file:// is not a goal, because module scripts and fetch fail there. After the first load the app, including its weights, works offline through a service worker.
AccessPrivate. The site is for a closed group of students, not the public. The production deployment sits behind Cloudflare Access with an allow-list of student emails, and every response carries X-Robots-Tag: noindex. The GitHub repository is public, so weights and fixtures are never committed.
Pretrained weightsBundled at build time by the developer. The developer runs scripts/convert.py locally, and the build copies the int8 artifact into dist/. The checkpoint has no declared license, which is why the deployment must stay private. Students cannot import, swap, or modify the weights or the tokenizer.
Weight formatW_E and W_U stored as int8 with symmetric per-token FP16 scales. Everything else stored as FP16. All compute is f32. A full-precision FP16 artifact also exists, used for reference and testing.
ParityTwo tiers. (1) The FP16 artifact must match TransformerLens tightly. (2) The drift of the int8 artifact from FP16 is bounded and reported.
TokenizerFull free-text BPE, exactly matching EleutherAI/gpt-neox-20b.
GenerationIncluded: greedy decoding only (argmax, with no temperature or top-k), with step-by-step replay. It is deterministic, so no sampling PRNG is needed.
AblationZero ablation only.
Activation explorerLists every hook, but tensors are materialized lazily.
AudienceStudents at ARENA level: plain-English explanations alongside the exact math and tensor shapes.
User controlsThe model and tokenizer are fixed. Students control prompts, generation, head selection, ablation, the backend choice, and the visualizations. They have no weight or tokenizer settings.

Role and deliverable

Deliver a production-quality Vite + TypeScript static web app. Assume the user is studying a compact induction circuit and wants short, exploratory feedback loops in the browser. Keep dependencies minimal. These are allowed:

  • @huggingface/tokenizers, a pure-TS tokenizer of about 8 KB gzipped;
  • a small Rust crate compiled to WASM;
  • dev and test tooling.

Do not use UI frameworks heavier than a small reactive library, or none at all. Do not use chart libraries larger than about 50 KB gzipped; hand-written SVG or Canvas is preferred.

If WebGPU compute is unavailable, the same model must run on the WebAssembly path with outputs that match within the tolerances below. The UI must always show the active backend.

Hard privacy rule: the app must never transmit tokens, text, activations, weights, telemetry, or analytics. The only network traffic allowed is same-origin requests for the app's own static assets. A Content-Security-Policy enforces this (see below).

Target model

Implement this exact TransformerLens configuration, which is the one used in ARENA 1.2:

HookedTransformerConfig(
  d_model=768,
  d_head=64,
  n_heads=12,
  n_layers=2,
  n_ctx=2048,
  d_vocab=50278,
  attention_dir="causal",
  attn_only=True,
  tokenizer_name="EleutherAI/gpt-neox-20b",
  seed=398,
  use_attn_result=True,
  normalization_type=None,
  positional_embedding_type="shortformer"
)

Forward-pass semantics. These match TransformerLens 2.x, and the README must document them.

tokens: [pos]                     # BOS = id 0 ("<|endoftext|>") prepended by default
embed      = W_E[tokens]          # hook_embed       [pos, 768]
pos_embed  = W_pos[0..pos)        # hook_pos_embed   [pos, 768]
resid_pre0 = embed                # shortformer: W_pos is NOT added to the residual stream
for L in 0..1:
  qk_in = resid_preL + pos_embed  # W_pos enters Q and K inputs only
  v_in  = resid_preL              # V gets no position embedding
  q = qk_in @ W_Q[L] + b_Q[L]     # attn.hook_q  [pos, 12, 64]
  k = qk_in @ W_K[L] + b_K[L]     # attn.hook_k
  v = v_in  @ W_V[L] + b_V[L]     # attn.hook_v
  scores  = (q · k) / sqrt(64)    # attn.hook_attn_scores [12, qpos, kpos]; masked kpos > qpos
  pattern = softmax(scores, -1)   # attn.hook_pattern
  z       = pattern @ v           # attn.hook_z  [pos, 12, 64]
  result  = z @ W_O[L]            # attn.hook_result [pos, 12, 768] (per head, before summing)
  attn_out = Σ_h result + b_O[L]  # hook_attn_out
  resid_post = resid_preL + attn_out   # hook_resid_post (no MLP, no LayerNorm, no resid_mid)
logits = resid_post1 @ W_U + b_U  # [pos, 50278]
  • Use TransformerLens hook names exactly: hook_embed, hook_pos_embed, blocks.{L}.hook_resid_pre, blocks.{L}.attn.hook_{q,k,v,attn_scores,pattern,z,result}, blocks.{L}.hook_attn_out, blocks.{L}.hook_resid_post. Also expose ARENA cache aliases, for example cache["pattern", 0].
  • Masking: TransformerLens uses -inf. Kernels may use a large finite negative value, but the masked probabilities must come out exactly 0.
  • Row 50277 of the vocabulary is an unused padding row. The tokenizer's highest ID is 50276. Show this in the UI.
  • The bias tensors exist in the checkpoint. ARENA describes the model as having "no biases", which suggests they are approximately zero. The converter must report each bias's maximum absolute value, and the forward pass must still apply the biases.
  • Model identifiers shown in the UI and docs: the TransformerLens config above and callummcdougall/attn_only_2L_half.

Organize the numerics as one op graph with three interchangeable executors that share a single analysis layer:

  • a WebGPU executor (primary);
  • a WASM executor (fallback);
  • a plain TypeScript Float32Array reference executor, which serves as the test oracle and is not shown in the UI.

Caching, hooks, ablation, and every analysis must work identically on all executors.

Model data and provenance

Upstream checkpoint facts. Embed these in convert.py (for verification) and document them in the README:

Repocallummcdougall/attn_only_2L_half, commit 3a3d92c6d6491233925c2649582128538a16843a
Fileattn_only_2L_half.pth, 183,933,661 bytes, SHA-256 7c8ccf06cc7d1a8c4820285d32fafd74f3b553c9af1b6765a1fbad094070578f. Appears to be FP16.
LicenseNone declared on the repo, and none on the ARENA materials repo. The weights are therefore served only from the private, access-controlled deployment. The README records this and the reason for it.
Parameters83,574,886: W_E and W_U each 38,613,504; W_pos 1,572,864; 2,362,368 per attention layer, including biases; b_U 50,278. Buffers (mask, IGNORE) are dropped and rebuilt on the client.

Artifact format. A manifest.json containing:

  • format version and upstream SHA-256;
  • for each tensor: name, shape, dtype, quantization, and the shard plus byte range;
  • for each shard: size and SHA-256;
  • the maximum absolute value of each bias tensor;
  • the int8-vs-fp16 drift report (tier-2 metrics), computed by convert.py;
  • the versions of convert.py, torch, and transformer-lens used;
  • the artifact checksum, defined as the SHA-256 of the canonical manifest.

Tensor data lives in content-hashed binary shards of at most 20 MiB, little-endian. The 20 MiB cap keeps each shard under Cloudflare Pages' 25 MiB per-file limit. Two variants:

  • int8 (deployed, about 90 MB):
    • W_E is quantized per row (per token).
    • W_U is quantized per column (per output token).
    • Quantization is symmetric with scale = max|x| / 127, stored as FP16.
    • All other tensors are FP16.
  • fp16 (reference, about 167 MB): every tensor in FP16, bit-identical to the checkpoint. Used locally for parity tests and never deployed.

Developer workflow:

  1. scripts/convert.py, run once by the developer:
    • Pinned to torch and transformer-lens==2.17.*; document any version it cannot run with.
    • Downloads the checkpoint once and verifies its SHA-256.
    • Quantizes the weights and writes both artifact variants to a gitignored weights/ directory.
    • Writes reference fixtures (see Testing).
  2. Build: vite serves weights/int8/ in development. npm run build copies the int8 manifest and shards into dist/weights/. A build check verifies every shard's SHA-256 against the manifest. The build fails if weights/ is missing, a checksum mismatches, or any fp16 shard or .pth reaches dist/.

At runtime, the app fetches the manifest and shards same-origin, verifies each shard's SHA-256 before use, and loads them into the worker. There is no import UI, and students cannot replace the weights.

Synthetic model (development and tests only).

  • It is generated deterministically from a fixed seed. It lets tests and contributors without the checkpoint exercise every code path. It is never deployed.
  • It has the exact architecture and is hand-constructed with a planted circuit: L0 head 7 is a previous-token head via a positional QK circuit, and L1 heads 4 and 10 are induction heads that K-compose with 0.7 and have a copying OV circuit. Every analysis therefore shows meaningful structure.
  • It is selected only through a dev-server flag, or a separate test build mode (npm run build:test) used by CI. The test build needs no weights/ and is never deployed. When the synthetic model is active, a persistent banner labels it “Synthetic — not pretrained”.
  • The README explains how the circuit was planted.

Never fetch model data from Hugging Face, GitHub, or any other remote at runtime.

Tokenizer

  • Use @huggingface/tokenizers with tokenizer.json and tokenizer_config.json from EleutherAI/gpt-neox-20b (Apache-2.0, about 2.1 MB raw, about 593 KB gzipped). They are pinned to a specific Hugging Face revision, with each file's SHA-256 recorded and checked in a test. They are vendored as static assets with attribution and are not imported into the JS bundle.
  • Encode without post-processor special tokens, then prepend BOS id 0 when “prepend BOS” is on (the default), matching TransformerLens to_tokens.
  • Handle these correctly:
    • NFC normalization;
    • the 23 added whitespace-run tokens (ids 50254–50276), matched before pre-tokenization;
    • byte-level display, rendering Ġ and Ċ legibly and showing partial UTF-8 tokens as bytes or � rather than mangled text.
  • Users can also enter raw token IDs and generate random-token sequences.

Runtime and backends

  • Run model execution in a dedicated Web Worker so the UI never blocks.
  • WebGPU:
    • f32 compute; do not use shader-f16.
    • Int8 weights are packed four per u32 and unpacked in WGSL, using unpack4xI8 when the packed_4x8_integer_dot_product language feature exists and manual bit extraction otherwise.
    • Each embedding matrix stays within the default 128 MiB maxStorageBufferBindingSize. Check the adapter limits and fail over to WASM with a clear message if they are insufficient.
    • Handle device.lost: stop all in-flight work immediately, show the reason, and offer “retry WebGPU” or “switch to WASM”.
  • WASM:
    • A small Rust crate built with wasm-bindgen and +simd128, single-threaded, loaded through Vite ?init or vite-plugin-wasm.
    • Kernels: matmul, fused int8-dequant matmul, masked softmax, and the attention einsums.
    • The dequantization formula and reduction order must be documented and shared with WGSL.
    • WASM threads are out of scope for v1, so cross-origin isolation is not required.
  • A backend selector offers Auto / WebGPU / WASM. Auto picks WebGPU when an adapter and device are obtained and otherwise falls back silently but visibly. Switching backends re-runs the current prompt and shows the max-abs-diff against the previous backend.
  • Deployment headers (public/_headers):
    • CSP: default-src 'self'; connect-src 'self'; script-src 'self' 'wasm-unsafe-eval'; worker-src 'self' blob:; img-src 'self' data: blob:; style-src 'self'; object-src 'none'; base-uri 'self'; frame-ancestors 'none'
    • X-Robots-Tag: noindex, nofollow on every path.
    • Cache-Control: private, max-age=31536000, immutable for hashed assets and weight shards. Use private because the site sits behind Cloudflare Access.
    • A short cache lifetime for index.html and the service worker.
  • Service worker: caches the app shell, the WASM, the tokenizer, and the weight shards for offline use. Shards are content-hashed, so they are cached once and never revalidated. Call navigator.storage.persist() so the roughly 90 MB of weights is not evicted. On first load, show a weights download progress bar based on the byte sizes in the manifest, not on Content-Length.

Interactions and UI

Provide a clean, information-dense app shell with a responsive but research-oriented layout. The workflow should feel like CircuitsVis meets Transformer Explainer.

  • Model status bar:
    • the model name (attn_only_2L_half, int8);
    • active backend;
    • artifact checksum (short form, with a copy button).
  • Prompt controls:
    • Free text, with live tokenization shown as token chips.
    • A raw token ID input.
    • A prepend-BOS toggle.
    • A repeated random-token generator: [BOS, r, r], where r has length seq_len, default 50, and comes from a seeded PRNG with the seed shown.
    • A sequence-length control and a run/cache button.
    • Validation: reject inputs longer than n_ctx, and warn above a soft default cap of 512 tokens.
  • Generation:
    • Greedy decoding only. The next token is the argmax of the last position's logits, with ties broken by the lowest token ID. There are no temperature, top-k, or seed controls. Only the final position's logit row is computed.
    • A max-new-tokens setting (default 20) is the only generation parameter. Generation stops early at n_ctx.
    • Step, play, pause, and replay controls that animate how attention patterns grow as tokens are appended.
    • Every step's cache can be inspected.
    • Generation reuses the KV cache, or recomputes for short sequences, which is acceptable.
  • Token table: for each position show:
    • token ID and decoded string;
    • role: BOS, first half, second half, or induction target;
    • log-prob of the actual next token and its per-token loss;
    • top-5 predictions with probabilities;
    • direct-path vs layer-0 vs layer-1 contribution to the correct logit.
    Highlight the repeated halves when a repetition is detected.
  • Activation explorer:
    • A searchable, sortable tree of every hook, showing name, shape, dtype, and size.
    • Tensors are materialized lazily, only when expanded, previewed, or exported.
    • Never materialize full [pos, 50278] logits unless explicitly requested, and show a size warning when that happens.
    • Slicing by layer, head, and position before viewing.
    • Export the selection locally as JSON, CSV, or .npy, with a size estimate shown before export.
  • Attention overview:
    • For each layer, a grid of 12 head cards. Each card holds a dest×source heatmap with tokens on both axes.
    • Causally impossible cells are drawn as visibly masked, using a hatched pattern rather than just a color.
    • Tooltips show exact values.
    • Color-scale controls: linear or log, and shared or per-head range.
    • Each card shows the head's score badges.
  • Head detail view:
    • An enlarged heatmap with zoom and pan.
    • Configurable destination and source bands.
    • Overlays for the induction stripe (offset 1 − seq_len) and the previous-token stripe.
    • A table of exact values.
    • Q, K, and V decomposition for the selected cell.
  • Circuit graph:
    • An interactive node-link diagram of tokens, heads, and the induction circuit.
    • Node size and color encode a chosen score or ablation effect.
    • Edge labels show the composition type and score, or the attention weight.
    • The canonical circuit diagram (0.7 → 1.4 and 1.10) uses a static, deterministic layout.
  • Timeline and run stats:
    • Total runtime, broken down into tokenize, forward/prefill, cache build, and analysis.
    • Sequence length and backend.
    • Memory:
      • GPU buffer bytes, from a ledger that wraps createBuffer and destroy;
      • the WASM heap size;
      • performance.measureUserAgentSpecificMemory(), only when it is available. Otherwise show “n/a”.
  • About footer: a short link to the model source (callummcdougall/attn_only_2L_half), the ARENA 1.2 material, and the tokenizer attribution with its Apache-2.0 license. Provenance details live in the README, not in the UI.

Interpretability analyses

Reproduce the ARENA 1.2 definitions exactly, and document each formula in the UI with an info popover and in the README. P = pattern[L][h] has shape [q, k].

  1. Attention head classifier.
    • ARENA detectors:
      • current-token = mean(diag(P))
      • previous-token = mean(diag(P, −1))
      • first-token = mean(P[:, 0])
      • induction = mean(diag(P, 1 − seq_len)) on [BOS, r, r]
      The default threshold is 0.4, and it is configurable.
    • Also offer TransformerLens detect_head patterns (previous_token_head, duplicate_token_head, induction_head), with the mul and abs error measures and exclude_bos / exclude_current_token.
    • Show a 2×12 grid with scores, thresholds, and a plain-English reason for each label, for example “prev-token score 0.93 > 0.4”.
  2. Per-token loss and direct logit attribution.
    • Per-token loss is −log_softmax(logits)[s, tok[s+1]], plotted with the first and second halves marked and their means shown.
    • DLA follows ARENA logit_attribution:
      • W_c = W_U[:, tokens[1:]]
      • components are [embed, 12 × L0 result, 12 × L1 result], giving shape [seq−1, 25]
      • attribution = einsum(W_c, component[:-1])
      W_U is not centred, and b_U and b_O are excluded but reported.
    • Show a per-head chart and a combined direct / L0 / L1 stacked chart for each position.
    • Explain in plain English why the loss drops in the second half: induction heads copy the token that followed the earlier occurrence.
  3. Zero ablation.
    • Toggle any set of heads to be zero-ablated at hook_z, i.e. z[:, h, :] = 0. A per-head option ablates at hook_v instead, to reproduce ARENA's ablation of 0.7's values.
    • Report the change in loss (ablated minus clean), using ARENA's get_ablation_scores convention: loss over the last seq_len − 1 positions.
    • Report changes in attention patterns and in head scores, especially the induction score of 1.4 and 1.10.
    • Provide a one-click “ablate each head” sweep that produces a 2×12 heatmap of loss increase.
  4. Circuit composition.
    • Definitions:
      • comp(W_A, W_B) = ‖W_A W_B‖_F / (‖W_A‖_F ‖W_B‖_F)
      • W_OV = W_V W_O and W_QK = W_Q W_Kᵀ, each 768×768 but rank 64
      Compute them with factored low-rank products and never materialize 768×768 products unnecessarily.
    • For each pair of L0 head i and L1 head j:
      • Q-composition = comp(W_OV⁰ᵢ, W_QK¹ⱼ)
      • K-composition = comp(W_OV⁰ᵢ, (W_QK¹ⱼ)ᵀ)
      • V-composition = comp(W_OV⁰ᵢ, W_OV¹ⱼ)
      Each is shown as a 12×12 grid.
    • Random baseline, as in ARENA: 300 samples of products of [768, 64] Kaiming-uniform factors, reporting mean and standard deviation. Show scores both raw and baseline-subtracted.
    • Highlight 0.7 → 1.4 and 0.7 → 1.10 K-composition.
  5. Full circuits.
    • The OV circuit W_E W_OV W_U for 1.4, for 1.10, and for the two stacked together. Report top-1 and top-5 accuracy along the diagonal, computed in row batches and never materializing 50278² entries at once.
    • The positional QK circuit for 0.7: W_pos W_QK W_posᵀ / 8, masked and softmaxed.
    • decompose_qk_input and the decomposed attention scores for 1.4, over the 14 components [embed, pos_embed, 12 L0 heads].
  6. End-to-end induction narrative. A guided, stepwise walkthrough of the canonical path:
    1. The first-half token A is followed by B.
    2. Previous-token head 0.7 at the first B attends to A and writes “previous token was A” into the residual stream through its OV circuit.
    3. The second-half A queries in 1.4 and 1.10.
    4. Through K-composition with 0.7's output, those queries match the key at the first B.
    5. The heads attend to the first B.
    6. Their OV circuit copies B into the logits.
    Each step links to and highlights the exact tokens, attention cells, tensors, weight matrices, and scores involved. The steps work on any repeated sequence the user picks, not only a hard-coded one.

Data, state, and performance

  • Keep parameters and activations in typed arrays or GPU buffers.
  • Cache activations in memory, keyed by (artifact checksum, tokens, ablation set, backend). Persist to IndexedDB only for short sequences, and evict on an LRU basis.
  • Debounce filters and redraws. Render large heatmaps with Canvas and small or interactive ones with SVG.
  • Never materialize full-vocabulary logits unless asked. Loss, DLA, and top-k only need targeted W_U columns or a streamed max and log-sum-exp.
  • Keep sequences short by default (repeated tokens with seq_len = 50 gives 101 tokens). Validate before dispatching GPU work.
  • Performance targets on a recent laptop with WebGPU, for a 101-token forward pass with a full cache: no more than 150 ms on WebGPU and no more than 1.5 s on WASM. Report the measured times.
  • Bundle budget: application JS no more than 250 KB gzipped and WASM no more than 150 KB gzipped, excluding the tokenizer JSON.

Quality and accessibility

  • Compact and comfortable density modes. Full keyboard navigation, including arrow keys to move across heatmap cells and Enter to select.

Testing and verification

  • CI vs local: CI (on the public repo) never has access to weights or fixtures. It runs type-check, lint, unit tests, tokenizer tests, synthetic-model parity, and the Playwright suite against npm run build:test. The production build (npm run build), the real-weight tests, and deployment are local-only. Before each deploy, the developer runs npm run verify:release. This runs the full suite, including tier-1 and tier-2 parity and the e2e suite against the production build, followed by the build checks.
  • Fallback tests stub navigator.gpu as undefined, and separately stub requestAdapter() to resolve to null.
  • If WebGPU cannot run in the environment, the WASM and reference paths must still be fully tested, and the report must say so.

There is also an in-app Verify panel. It runs the backend parity checks in the student's browser on the active backend, and displays the build-time drift report and bias maxima from the manifest. The fp16 artifact is not deployed, so tier-2 parity cannot be rerun in the browser.

  • Backend parity: WebGPU vs WASM vs the TS reference, using fixture tensors at sequence lengths 1, 8, 101, and 512.
    • Per-kernel tolerance: rtol = 1e-4, atol = 1e-5.
    • Logits after the full model: atol = 1e-3, rtol = 1e-3, with identical top-5 sets.
    • Greedy generation yields identical token sequences on all executors. The only allowed difference is at a step where the top-2 logit margin is below the logits tolerance.
  • Model parity, tier 1 (FP16 artifact vs TransformerLens):
    • convert.py writes fixtures from TransformerLens: tokens, which include ARENA's exact repeated-token batch because PyTorch's RNG cannot be reproduced in the browser; selected activations (patterns, z, result, resid_post); logit slices; and analysis outputs (detector scores, induction scores, DLA, ablation scores, composition grids).
    • Required tolerances: patterns atol = 1e-4, logits atol = 1e-3, DLA sum identity atol = 1e-3.
    • The fixtures are small, gitignored, and live with the weights. Tier 1 runs locally in verify:release and is skipped with a visible notice when the fixtures are absent, as in CI. The synthetic-model fixtures always run.
  • Model parity, tier 2 (int8 vs FP16): report and assert:
    • top-1 agreement on at least 99% of positions;
    • mean loss difference of no more than 0.05 nats;
    • identical head classifications;
    • induction and detector scores within 0.02.
  • Tokenizer: exact ID equality against Python-generated fixtures. The corpus covers multiple spaces, tabs, newlines, contractions, digits, emoji, combining accents, CJK, leading spaces, and the ARENA sample text.
  • Analysis correctness: unit tests on small hand-built tensors for:
    • the detector diagonals, including the 1 − seq_len offset;
    • detect_head with mul and abs;
    • the DLA identity (sum of components equals the correct-token logit minus the bias terms);
    • ablation effects;
    • composition scores against a dense computation;
    • top-k circuit accuracy.
  • Weights loading and build:
    • The loader verifies each shard's SHA-256, and rejects a corrupted shard with the failure state above.
    • The build fails when weights/ is missing or a shard checksum mismatches.
    • The vendored tokenizer files match their recorded SHA-256 values.
  • Privacy:
    • The Playwright suite records all network requests during a full session (load, run, generate, export). It asserts that every one is same-origin, and that only static assets and weight shards are requested.
    • A test asserts that the CSP and X-Robots-Tag headers are present in _headers.
    • A build check asserts that dist/ contains exactly the int8 shards listed in the manifest, with no fp16 shards, .pth, or fixtures.
  • Interaction tests:
    • backend switching, including auto-fallback;
    • token selection and hover coordination;
    • heatmap rendering;

Acceptance criteria

  1. With weights/ present, npm ci && npm run build produces a static dist/ that runs under vite preview and deploys to Cloudflare Pages unchanged. dist/ contains the verified int8 artifact and nothing from the fp16 variant, and every file is under 25 MiB. Without weights/, the build fails with a clear message.
  2. On first load, the pretrained int8 weights download with a progress bar, pass checksum verification, and run end to end on WebGPU or WASM. No synthetic banner or synthetic code path is reachable in production.
  3. CI passes on a fresh clone with no weights/, running the e2e suite against npm run build:test. npm run verify:release passes locally with the real weights.
  4. After a reload with the network disabled, the cached app and weights load from the service worker and the app works fully offline.
  5. On repeated random tokens (seq_len = 50, batch 10):
    • heads 1.4 and 1.10 are classified as induction heads (score > 0.6), with 1.10 above 1.4;
    • head 0.7 is classified as a previous-token head;
    • the mean loss on the second half is far below the first (about 3.4 vs about 14 in ARENA's sample; require at least a 3× reduction).
  6. In the K-composition grid, 0.7 → 1.4 and 0.7 → 1.10 are the two largest entries and exceed the random-baseline mean by at least 3σ. V-composition into 1.4 and 1.10 is near the baseline.
  7. Full OV circuit top-1 diagonal accuracy is about 30.8% for 1.4 alone and about 95.6% for 1.4 and 1.10 stacked, within ±2 percentage points on FP16.
  8. Zero-ablating 0.7 at hook_v drops 1.4's induction score from about 0.68 to near 0. The ablate-each-head sweep ranks 0.7, 1.4, and 1.10 as the most harmful to ablate.
  9. The DLA components sum to the correct-token logit (excluding biases) within atol = 1e-3 at every position.
  10. Tier-1 and tier-2 parity, backend parity, and tokenizer fixtures all pass at the tolerances stated above.
  11. The privacy test records zero cross-origin requests across a full session, and the CSP and noindex headers are deployed.
  12. Forcing WASM (by stubbing WebGPU) yields identical classifications and analyses, and the UI shows “WASM”.
  13. Every visualization has an accessible text or table equivalent. The main workflow (enter prompt → run → select head → view detail → ablate) is completable by keyboard alone.
  14. The performance targets and bundle budget are met, or any miss is reported with measurements.
  15. Every interaction in the narrative's six steps highlights the correct tokens, cells, and tensors on a user-chosen repeated sequence.
